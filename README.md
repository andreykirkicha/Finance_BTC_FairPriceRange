# Данные для интервалов цен BTC-опционов

Сборщик одного снимка котировок **BTC inverse call** на основной бирже Deribit.
По умолчанию дата экспирации — **25 декабря 2026 года**, страйки — около базисной
цены опциона. Каждый контракт даёт одну строку. Нужен Python **3.10+**;
Для сборщика API-ключ, аккаунт и сторонние библиотеки не требуются.
Этап расчёта IV использует SciPy; см. раздел ниже.

## Запуск

Из корня проекта:

```bash
python3 -m deribit_data
```

Параметры можно задать явно:

```bash
python3 -m deribit_data \
  --expiry 2026-12-25 \
  --max-log-moneyness 0.15 \
  --max-relative-spread 0.20 \
  --output-dir data
```

Справка: `python3 -m deribit_data --help`. Сборщик обращается к сети один раз
для списка контрактов и один раз для общего снимка всех BTC-опционов;
при временной ошибке повторяет запрос максимум трижды. Повторный запуск
создаёт отдельный снимок, не перезаписывая предыдущий. Это текущие котировки:
запуск завтра не восстановит сегодняшний снимок.

## Файлы результата

Каждый запуск создаёт `data/<время_запуска_UTC>/`:

| Файл | Содержимое |
| --- | --- |
| `instruments_raw.json` | Полный ответ со спецификациями, параметрами запроса и временем получения |
| `summaries_raw.json` | Полный ответ общего снимка котировок и информация о запросе |
| `all_calls.csv` | Все inverse call нужной экспирации, включая исключённые |
| `atm_calls.csv` | Контракты, прошедшие фильтры, для последующего расчёта IV |
| `metadata.json` | Параметры отбора, источник времени, числа строк, причины исключения, предупреждения и статус |

`status=ok` означает, что есть подходящие строки; `empty` — снимок получен,
но ни один контракт не прошёл фильтры; `failed` — сбор или обработка завершились
ошибкой. Коды завершения команды: соответственно **0**, **2**, **1**.
При ошибке уже полученные исходные ответы сохраняются. Если требуемой экспирации
нет, программа показывает доступные даты и не выбирает другую автоматически.

## Что означает отбор ATM

Используем `F = underlying_price` из того же ответа, что и bid/ask опциона.
Deribit определяет это поле как базисную цену, используемую при расчёте IV;
`underlying_index` сохраняет название соответствующего фьючерса либо `index_price`.
Для проекта нужно проверить, что этот базис соответствует выбранному форварду:
мы не подменяем его ценой бессрочного фьючерса или последней сделкой BTC.

Фильтр `|ln(K/F)| ≤ 0.15` оставляет страйки примерно от **86.07% до 116.18% F**.
Ближайший единственный страйк не выбирается: для оценки квантилей нужна группа.
Значение `0.15` — начальная настройка, а не установленная исследованием граница.
Ограничение спреда `(ask-bid)/mid ≤ 0.20` тоже предварительное.

Диапазон расширен с `0.05` до `0.15`, чтобы увеличить число наблюдений.
В сохранённом снимке от 16 ноября 2026 года получены такие результаты
при одинаковом ограничении спреда 20%:

| Максимальное \|ln(K/F)\| | Контрактов после всех фильтров |
| --- | --- |
| 0.05 | 5 |
| 0.10 | 7 |
| **0.15 (по умолчанию)** | **13** |
| 0.20 | 17 |
| 0.25 | 20 |

Это сравнение одного и того же снимка, а не гарантированное число контрактов
в следующих запусках. Ослабление ограничения спреда в диапазоне `0.15`
не добавляло контрактов. Более широкий диапазон включает опционы дальше от ATM,
поэтому влияние страйка на распределение IV нужно учитывать при моделировании.
У параметров командной строки и `Filters` теперь единый источник значений
по умолчанию.

Контракт исключается из `atm_calls.csv`, если он неактивен, нет положительных
bid/ask, bid выше ask, отсутствует корректная базисная цена, спред слишком широк,
страйк вне диапазона ATM, контракт истёк или mid выходит за диапазон формулы
из PDF: `max(1-K/F, 0) < mid < 1`. Граничная цена с нулевой IV также исключается.
Все причины сохраняются в `all_calls.csv` в поле `exclusion_reasons`.

Временные ограничения:

- `--max-summary-age-seconds 10`: возраст записи summary относительно времени
  ответа сервера `usOut` не более 10 секунд; при отсутствии `usOut` используется
  местное время UTC, о чём пишется предупреждение.
- `--max-snapshot-span-seconds 5`: времена записей прошедших остальные фильтры
  контрактов различаются не более чем на 5 секунд; иначе они все исключаются.

**Один REST-ответ — приближённый общий снимок, а не гарантия атомарности.**
`creation_timestamp` относится к записи summary и не сообщает время последнего
изменения каждой заявки в стакане. Поэтому проверка возраста summary не доказывает
свежесть отдельных заявок. Для строгой синхронизации понадобится поток WebSocket.

## Поля для следующего этапа

| Поле | Назначение / единицы |
| --- | --- |
| `instrument_name` | Идентификатор контракта; по нему можно зафиксировать отложенную группу |
| `strike_usd` | Страйк K, USD за BTC |
| `underlying_price_usd` | Базисная цена F, USD за BTC |
| `underlying_index` | Источник базисной цены Deribit |
| `bid_btc`, `ask_btc`, `mid_btc` | Премия в BTC; mid вычисляем как `(bid+ask)/2` |
| `expiration_utc`, `summary_utc` | Экспирация и время наблюдения UTC |
| `time_to_expiry_years` | T: фактическое число секунд до экспирации / (365 × 86400) |
| `days_to_expiry` | Фактический остаточный срок; он не заменяется константой «30 дней» |
| `log_moneyness` | ln(K/F) |
| `relative_spread` | (ask-bid)/mid, доля, а не проценты |
| `mark_iv_exchange_pct` | IV биржевой mark-цены, в процентах; только для диагностики |
| `interest_rate_exchange` | Ставка из API в исходном представлении; сохраняется без преобразований |

`last_btc` и `mark_btc` сохраняются справочно и не заменяют отсутствующий mid.
Восстанавливать собственную IV методом Брента предстоит по `mid_btc`:
**готовая `mark_iv` биржи в выборку IV не подставляется**.

При менее чем 20 прошедших фильтры контрактах выводится предупреждение:
хвостовые квантили на малой выборке нестабильны, а после выделения отложенной
группы наблюдений останется ещё меньше. Это диагностический порог,
а не статистическая гарантия. Сборщик не расширяет ATM-диапазон самостоятельно.
Повторные снимки не следует автоматически объединять в одну выборку: это разные
моменты рынка. Деление на обучающую/отложенную группы, расчёт IV, квантилей и
ценовых интервалов относятся к следующему этапу проекта.

Счётчики объёма за 24 часа и открытый интерес сохраняются справочно.
Объём может включать сделки с отложенной публикацией, а открытый интерес
публикуется с задержкой. Они не служат подтверждением свежести котировок
или наличия достаточной ликвидности на лучшем bid/ask.

## Расчёт IV по историческому дампу

Для этапа IV используется `scipy.optimize.brentq`. Установите SciPy (поддерживается
Python 3.10+):

```bash
python3 -m pip install "scipy>=1.15"
```

Расчёт по последнему снимку BTC call в дампе:

```bash
python3 -m deribit_data.iv_pipeline \
  --dump datasets/dump_2024-11-09_00_46_57.sql.gz \
  --output-dir results
```

По умолчанию берётся `current_time` последнего снимка; другой снимок можно задать
через `--snapshot 2024-06-04T08:57:48.287611`. Повторный запуск требует `--force`.

Результаты:

| Файл | Содержимое |
| --- | --- |
| `results/iv_<снимок>.csv` | Только успешно посчитанные IV и их рыночный контекст |
| `results/iv_<снимок>_summary.json` | Воронка фильтров, статистика IV, параметры Brent, версии |
| `results/iv_report_<снимок>.md` | Отчёт с методикой, данными и ограничениями |

Что считается:

- только BTC inverse call; ETH, puts и неактивные строки не используются;
- `F = underlying_price`, `r = 0`, `mid = (bid_price + ask_price) / 2`;
- `T` — UTC, ACT/365F; годы `0024`/`0025` исправляются на `2024`/`2025`;
- полночь в `expiry` трактуется как фактическое время Deribit `08:00 UTC`;
- ATM-фильтр `|ln(K/F)| ≤ 0.15`, минимальный срок `T ≥ 1 дня`;
- биржевая `mid_IV` используется только для диагностики и не подставляется в результат.

Первый расчёт по снимку `2024-06-04 08:57:48 UTC` оставил 148 контрактов из 462.
Подробности и статистика отсева — в `results/iv_report_20240604T085748Z.md`.

## Проверка кода

Тесты работают без сети и используют синтетические данные; для IV-этапа нужен SciPy:

```bash
python3 -m unittest discover -s tests -v
```

Они проверяют единицы и сроки, фильтры, отсутствие подмены mid ценами mark/last,
контроль времени, экспорт, сохранение исходных ответов, парсинг COPY-блока,
round-trip восстановления IV и поведение при API-ошибках.
